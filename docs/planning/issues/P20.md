# [P20] Build responsive settings, general preferences, and appearance controls

> Current scope (2026-10-02): Windows x64 only. macOS is deferred and is not a dependency or release gate. #55 removes its implementation. Use minimal functional service tests, one canonical test per flow; native/UI qualification remains manual. This supersedes older cross-platform acceptance text and historical comments.

Provide a reusable responsive shell for all five settings sections.

## Scope

- Implement side navigation at >=640 px and horizontally scrollable tabs below 640 px; stack labels/descriptions and controls while keeping switch rows inline.
- Create separate SettingsWindow, SettingsNavigation, SettingsSection, SettingsRow, GeneralSettings, and AppearanceSettings files; mount Tags, Shortcuts, and Storage sections through clear feature entrypoints.
- Wire launch at login, tray visibility, startup size mode, theme, and pin to immediate settings services; copying always keeps the window open and the legacy hide preference has no active control.
- Provide Windows visibility and native-operation status; ensure a working way to reopen Promptly before hiding tray routes.
- Handle rejected native preference changes with inline errors and rollback, without a Save button.
- Latest Settings refinement: show the running Electron app version, an inert disabled Check for updates control and a GitHub repository link through a fixed main-process route. Preserve storage import/export/clear, omit its data-location/reveal row and remove ellipses from action labels. Familiar tag Edit/Delete actions have icons, tooltips and accessible names; confirmation controls retain text.

## Acceptance criteria

- [ ] 639/640 px breakpoint behavior matches reference layouts and keyboard focus survives resizing.
- [ ] Every listed General/Appearance preference persists and takes effect immediately.
- [ ] Only supported Windows controls are present; close/back returns to the expected window.

## Verification

Extend the existing canonical public functional service flow only where needed; keep real internal services/storage and fake external OS/time boundaries. Run strict types, ESLint, Prettier, functional tests and Windows packaging. UI, native delivery, NVDA and distribution requirements are manual Windows release checks where relevant. Performance measurements and budgets are skipped for this pass. No automated GUI/E2E suite, duplicate flow tests, stress gates or new test infrastructure.
