# [P03] Validate native capture, keyboard hooks, and clipboard feasibility on Windows

> Current scope (2026-10-02): Windows x64 only. macOS is deferred and is not a dependency or release gate. #55 removes its implementation. Use minimal functional service tests, one canonical test per flow; native/UI qualification remains manual. This supersedes older cross-platform acceptance text and historical comments.

Resolve the platform risks before committing the production capture implementation.

## Scope

- Qualify the existing Windows UI Automation TextPattern adapter, foreground app identity and modifier hook through bounded manual checks; evaluate safe clipboard fallback separately. Do not add another native test harness.
- Compare maintained native packages against small packaged native helpers; record licenses, supported Electron ABI/architectures, permissions, helper lifecycle, and rebuild/signing needs. Select adapters behind stable interfaces.
- Test editors, Chromium browsers, terminals, no selection, revoked permission, Windows elevated apps, and protected input. Validate terminal-specific Copy behavior; Ctrl+C must not interrupt a running command.
- Investigate multi-format clipboard snapshots, ownership/change counters, unsupported/lazy formats, failure restoration, and crash behavior. If faithful restoration cannot be established, skip destructive fallback.
- Measure capture-to-feedback on each path. Confirm Alt+Space availability instead of assuming it.

## Acceptance criteria

- [ ] A documented support matrix contains real observations from Windows, with OS/architecture and app versions.
- [ ] Adapter choice and packaging proof exist for Windows; unsupported paths return explicit errors without overwriting the clipboard.
- [ ] The ADR records outstanding release blockers, including failures of the under-150-ms target; no untested claim of universal capture.

## Verification

Extend the existing canonical public functional service flow only where needed; keep real internal services/storage and fake external OS/time boundaries. Run strict types, ESLint, Prettier, functional tests and Windows packaging. UI, native delivery, NVDA, installation and performance requirements are manual Windows release checks where relevant. No automated GUI/E2E suite, duplicate flow tests, stress gates or new test infrastructure.
