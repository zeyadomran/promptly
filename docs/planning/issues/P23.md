# [P23] Build first-launch onboarding with a real practice capture

> Current scope (2026-10-02): Windows x64 only. macOS is deferred and is not a dependency or release gate. #55 removes its implementation. Use minimal functional service tests, one canonical test per flow; native/UI qualification remains manual. This supersedes older cross-platform acceptance text and historical comments.

Take new users from first launch to a successful capture using the real pipeline.

## Scope

- Build separate stepper, WelcomeStep, ShortcutStep, TryCaptureStep, and footer components matching 760×510 references.
- Use three Windows steps: Welcome, Shortcut, and Try Capture. No Accessibility permission screen, System Settings link, or polling is needed.
- Reuse shortcut recording/validation; display a selectable sample prompt and route its capture through the production capture pipeline.
- Show the real toast and Saved. Nice. only after successful persistence; enable Open Promptly on success and retain a Skip route.
- Persist completion, open Compact on finish, and retain a successfully captured practice snippet. Skip creates no fabricated snippet; unsupported capture remains recoverable with a clear explanation.

## Acceptance criteria

- [ ] The three-step Windows first-run flow works and does not repeat after completion.
- [ ] Practice success is backed by stored data, with no duplicate synthetic event or fake toast.
- [ ] Back/skip/restart/unsupported-capture paths remain usable and clean up listeners.

## Verification

Extend the existing canonical public functional service flow only where needed; keep real internal services/storage and fake external OS/time boundaries. Run strict types, ESLint, Prettier, functional tests and Windows packaging. UI, native delivery, NVDA, installation and performance requirements are manual Windows release checks where relevant. No automated GUI/E2E suite, duplicate flow tests, stress gates or new test infrastructure.
