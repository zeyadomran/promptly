# ADR: Native capture through packaged platform helpers

Status: **selected for production implementation; real-app release qualification incomplete**.
Evidence date: 2026-10-02. Scope: P03 / issue #5. Disposable implementation: `experiments/native-capture/`.

P09 now has a maintained [production Windows adapter](windows-selection.md) under
`native/windows/` and `src/main/platform/windows/`, including packaged-helper
integration, read-only warmup and watchdogs. Its narrower production protocol and
live identity activation boundary are documented there. The disposable spike's
keyboard/clipboard commands are not part of this production helper. Real-app
qualification and full capture-to-toast latency remain open.

## Decision and stable boundary

Use a persistent Swift helper on macOS and a small C# helper using the OS-installed .NET Framework on Windows. Both communicate only with Electron main through NDJSON v1 on inherited stdio. Ship executables outside ASAR through Forge `extraResource`; resolve the helper from a fixed application resource path, never from renderer input. The spike is unsigned; signing and notarization are explicitly left to the user.

The main-process adapters should expose `captureSelection(expectedPid)`, `getPermissions()`, `subscribeKeys(listener)`, `getClipboardMetadata()`, `tryClipboardFallback()` and `dispose()`. They translate helper results into typed domain results. Keep persistence, normalization, shortcut recognition and feedback out of native code. `SourceIdentity` is `{ pid, name, id }`, where `id` is a macOS bundle identifier or Windows executable basename, never an executable path or a document/window title. Public persisted provenance may use nullable `sourceAppId`; renderer create/update requests must not claim native provenance. Source activation must resolve an authoritative native identity in main and revalidate it; never shell-execute a supplied identity.

NDJSON requests contain `{ v: 1, id: string, command: string }`. `capture` accepts optional JSON integer `expectedPid` in 1–2,147,483,647 and exact JSON boolean `includeText`. Only omission defaults to an unguarded PID (`0` internally) or text omitted (`false`); supplied null, fractional/string/boolean PID, out-of-range PID and coerced text flags return `invalidRequest` before native access. Responses contain `v`, matching `id`, `status`, and command-specific data. Selection results are `ok`, `empty`, `unsupported`, `permissionDenied`, `secureInput`, `foregroundChanged`, `selectionTooLarge`, or `providerError`. Successful selection includes `source`, `characterCount`, `elapsedMs`, and `text` only when explicitly requested. The production adapter requests text through its private pipe; never log it. The experiment's driver prints fixture-only aggregates.

Selection size is capped at 1,048,576 UTF-16 units, with overflow rejected explicitly and never truncated. Helper serializers and client frames allow **6 × 1,048,576 + 65,536 = 6,356,992 UTF-8 bytes**, excluding the newline: six bytes per unit covers worst-case `\\uXXXX` JSON escaping, and the remaining allowance covers bounded IDs/source/envelope. Windows serializer character capacity matches this ceiling; both emitters check the final UTF-8 size and return a small `selectionTooLarge` response on overflow/serialization failure rather than crashing or emitting an oversized selection. The client enforces bytes, not JavaScript string length. `protocol-safety-check.mjs` uses an explicit `--protocol-fixtures` mode: malformed options are counted before native calls, and synthetic quotes/control/BMP/supplementary Unicode payloads test zero, max−1, max and max+1 units. Test-only payload/options/stats commands are unavailable without the flag. No user selection or clipboard content is involved.

Other commands: `capabilities`, `clipboardMetadata`, `fallback`, `hookStart`, `probeAltSpace`, `stop`. Unsolicited key records are `{ v: 1, type: 'key', modifier: 'shift'|'control'|'alt'|'meta'|'other', down, repeat, timestampMs }`; ordinary characters/key names are omitted. `other` cancels double-tap recognition. macOS may emit `hookDisabled`. Double-tap recognition belongs in P07 and must reset on hook loss, overlapping modifiers, repeats and ordinary keys. macOS aggregate modifier flags require particular care when both left/right keys are held; this spike does not prove physical-key tap recognition in that case.

Production lifecycle: start once, wait for capabilities, serialize requests, match bounded request IDs, validate every response, bound frames/queues, and enforce a watchdog. Timeout kills and replaces the helper; late data never reaches persistence. Close stdin/`stop` on quit and stop capture before teardown. Windows UIA providers can hang; process isolation allows terminating a blocked call without hanging Electron. Crash/timeout returns an explicit result. EOF exits helpers. This disposable client's 2-second watchdog proves process termination; it does not meet the 150-ms UX budget. Production should use a tighter capture deadline and measure actual toast latency. Move output off hook callbacks into a bounded queue before release: slow stdout must not disable a native hook.

## Selection, permissions and shortcuts

macOS reads `AXSelectedText` on the focused element of the frontmost application's AX tree, with a short AX messaging timeout. It checks Accessibility without requesting it, checks Secure Input and secure-field subrole, and verifies the foreground PID again after reading. The helper uses a passive session event tap, not a HID root tap or key suppression. It independently checks `CGPreflightListenEventAccess()` before installing the hook. This introduces **Input Monitoring** as a separate onboarding state to verify on actual macOS builds; Accessibility alone must not be advertised as sufficient. No Screen Recording, AppleScript automation or root permission is used. [Apple event taps](https://developer.apple.com/documentation/coregraphics/cgevent/tapcreate(tap:place:options:eventsofinterest:callback:userinfo:)), [listen permission preflight](https://developer.apple.com/documentation/coregraphics/cgpreflightlisteneventaccess()), [Secure Input](https://developer.apple.com/library/archive/technotes/tn2150/_index.html).

Windows reads only the focused element's `TextPattern.GetSelection()`. A missing provider returns unsupported rather than reading the whole document or a password. `IsPassword` is checked first. Selection retrieval is bounded at one Mi UTF-16 code units plus one overflow detection character. Foreground HWND is checked before/after; PID identifies the source. UIA cross-process text calls can exceed the budget. [TextPattern](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.textpattern.getselection), [UIA performance](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-understandingperformanceissues). UIPI/elevated/secure-desktop paths are not promoted by adding `uiAccess` or elevating Promptly; inaccessible providers fail explicitly. [Microsoft security overview](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-securityoverview).

Hook installation success is not evidence of real physical modifier delivery. Windows uses a passive `WH_KEYBOARD_LL` and always calls the next hook, ignores injected keys, and releases the hook on its message-loop exit. Real double-tap behavior remains a human test. macOS Secure Input prevents interception; report unavailable behavior and preserve selection/clipboard safety rather than trying to bypass it.

Alt+Space must be tested by actual `globalShortcut.register()` and its boolean return in P07. The Windows native registration probe releases immediately; local Windows 11 returned `shortcutUnavailable`. Windows Terminal documents Alt+Space as its system-menu binding. [Terminal bindings](https://learn.microsoft.com/en-us/windows/terminal/customize-settings/actions#open-system-menu). macOS probe intentionally returns unsupported because the actual Electron registration still needs testing. [Electron globalShortcut](https://www.electronjs.org/docs/latest/api/global-shortcut). Display the conflict and let the user select a binding; never quietly claim registration succeeded.

## Clipboard safety and terminal Copy

**Destructive fallback is disabled on both platforms.** The `fallback` command always returns `unsupported` with `faithful-all-format-snapshot-unproven`, `clipboardMutated: false`, `keysInjected: false`. There is no clipboard write or input injection API in this experiment. Production P10 must keep this safety gate until faithful restoration is established for the actual current clipboard.

Windows enumerates format IDs and records the sequence number and owner PID without calling `GetClipboardData`. Formats may be delayed-rendered, private, owner-display, GDI handles, or registered application-specific payloads. They cannot all be copied as HGLOBAL byte buffers. Reading a delayed format can invoke the owner or time out; faithfully restoring owner semantics after clearing is not proven. [Clipboard formats](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats), [sequence number](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclipboardsequencenumber), [delayed rendering](https://devblogs.microsoft.com/oldnewthing/20220609-00/?p=106731).

macOS enumerates advertised pasteboard types and `changeCount` without materializing bytes. Promised/lazy data and original ownership cannot be universally preserved by writing selected MIME-like formats. A plain text/HTML/PNG snapshot is insufficient evidence. [NSPasteboard](https://developer.apple.com/documentation/appkit/nspasteboard), [changeCount](https://developer.apple.com/documentation/appkit/nspasteboard/changecount). Counters can detect external changes but cannot identify which process made a change on their own. Restoring after a concurrent user copy would overwrite newer data, so it must be skipped. No restore exists here, which also makes failure/crash paths non-destructive. A metadata comparison is not a format round-trip test.

Never send generic Ctrl+C to terminals: with no selection it can interrupt a command. Windows Terminal exposes a configurable Copy action and Ctrl+Shift+C bindings can be changed; terminal identity alone cannot prove current bindings. [Terminal Copy](https://learn.microsoft.com/en-us/windows/terminal/customize-settings/actions#copy-text). Terminal-specific Copy through a verified menu/action, a faithful clipboard transaction and selection confirmation would all be prerequisites. Since the transaction prerequisite fails, the experiment sends **no Copy in any terminal**. A terminal UIA/AX provider may still provide selection directly. Running terminal commands were never interrupted during these checks.

### Latency receipts and interpretation

The [dual-platform native run](https://github.com/zeyadomran/promptly/actions/runs/36967522024), head `4181377`, supplied these figures, **n=10 sequential samples per newly launched fixture**. Exact fixture-only aggregates are preserved in [native-capture-evidence.json](native-capture-evidence.json). Native duration starts before querying foreground and stops after UIA/AX selection/source/final foreground verification; it excludes JSON/pipe delivery. Round-trip duration starts immediately before the driver writes a request and stops on parsing its reply; it excludes helper/fixture startup, persistence, shortcut recognition and toast display. Cold means the first request against that newly launched fixture. Only the selected fixture's first request is also the helper's first UIA/AX call; empty/password fixtures reuse an already initialized helper. Warm is the remaining nine requests. Percentiles use nearest rank (p50 index 4, p95 index 9 for n=10); this small sample is feasibility evidence, not a statistical performance guarantee.

Read-only UIA/COM initialization before declaring the helper ready is a plausible mitigation, alongside capture deadlines and dropping late results; neither mitigation has been implemented/measured in this disposable spike. Warm fixture durations do not establish real-app behavior or full capture-to-toast compliance. Production P09/P11/P28 must retain this release blocker until an actual integrated measurement passes.

This is actual controlled-app proof, not a claim that arbitrary background apps can be focused or read.
