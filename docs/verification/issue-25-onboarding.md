# Issue 25: Windows first-launch onboarding

The first ordinary window opens the three-step 760 × 510 setup surface until durable `onboardingComplete` is true. Welcome, Shortcut and Try Capture reuse the application fonts/logo, native caption area, shared recorder, validated SettingsService and production capture service. Back and Skip release recorder ownership; an accepted shortcut update settles before Continue. Completion saves Compact as the startup mode before opening its library and closing the tutorial.

Practice success is observed from main-only committed capture events. The retained native foreground window handle is validated as a 16-digit hexadecimal scalar and matched against the owned tutorial BrowserWindow handle; no integer coercion, window token, content or source metadata crosses the tutorial status channel. The status projection is versioned and restricted to that live registered document. Renderer destruction, crash, navigation and shutdown retire its listener. Ordinary library mutations do not qualify practice. Saved and duplicate events are eligible; empty/failed/unsupported results cannot enable Open Promptly. The existing confirmation overlay alone renders the actual committed preview and respects confirmation/theme preferences.

The sample is a readonly selectable textarea. Before creating an onboarding window, Electron's **app-wide runtime** accessibility support is enabled if needed. It remains enabled through quit to avoid disabling an assistive tool that becomes active during setup; no OS accessibility preference is changed. This follows the [Electron accessibility API](https://www.electronjs.org/docs/latest/api/app#appsetaccessibilitysupportenabledenabled-macos-windows), rather than a per-WebContents claim. Windows UI Automation still must expose a genuine selected TextPattern range; there is no clipboard fallback or synthetic practice write. If that provider is unavailable, Back and Skip remain available with a truthful explanation.
